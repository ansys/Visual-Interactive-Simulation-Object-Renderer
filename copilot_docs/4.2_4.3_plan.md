## 5. The four settled decisions

### D1 — S2c.2: where the local `SchemaVersionMismatchError` catch lives

**Decision.** In `useClientVtk`'s rebuild function (`onServerUpdateAsync`, moved unchanged in S2c.0), around the
single `await buildFrontendAsync(...)` call, inside the existing `try { … } finally { re-add listeners }`. The catch
is the same four lines as today's inner catch around `new VisorSceneDetails`:
`if (err instanceof SchemaVersionMismatchError) { setSchemaMismatchError(err); return; } throw err;`.

Effects, each the same as today [src: `App.tsx` `onServerUpdateAsync`]:
- the `finally` still re-adds `addServerUpdatedListener` and `addSetStateListener`;
- the `return` still skips the 100 ms `resizeAsync` timeout and the perf report after the `try`;
- `App` still renders the message from `schemaMismatchError` (moved out of App's state into the hook's return in
  S2c.0; the JSX is unchanged).

Why the catch can wrap the whole build and still catch only the parse: `SchemaVersionMismatchError` is constructed
in exactly one place, `VisorSceneDetails.tsx:40` (search `new SchemaVersionMismatchError` in client `src` → that one
match) [src], and `buildFrontendAsync` parses first, before `createRenderer` (§6 contract; S2c.2 pin 1).

Rejected:
- Catch in `App`: the rebuild runs inside an async function the effect fires and forgets; App has no frame to catch
  in, and the `finally`/early-return ordering would be lost.
- A wrapper that returns `VisorFrontend | SchemaVersionMismatchError`: reinstates the union ruling 15 removed.
- Catch inside `buildFrontendAsync`: it would have to signal the mismatch some other way (callback or union), the
  same objection.

`useServerVtk` (S3.3b) has its own four-line catch. **Ruling 12 duplicate:** named; its home would be
`buildFrontendAsync` only if ruling 15 were reversed. Proposal: keep the duplicate (four lines, mode-independent
shape, no logic to drift).

**Pin that the local mismatch display is unchanged** (S2c.2, written and run green *before* the extraction, then
green after): `jest-tests/AppSchemaMismatch.test.tsx` renders `<App />` with `./wasm/RemoteVtkScene` and
`./components/UiScaffold.tsx` mocked (factory mocks; jsdom has no `ResizeObserver`, which `UiScaffold.tsx:128`
uses [src]). The fake scene's `trameTriggerAsync('get_visor_scene_details_json')` resolves `{ schemaVersion: 3 }`.
Assertion: the page shows exactly
`Scene details schema version mismatch: payload is version 3, client expects version 4.` (hand-written literal;
the `4` is not imported, session rule 10c). Second assertion in the same test: `createAsync` on the mocked
`WasmRenderer` is never called. From S2c.3 on, the test also mocks `useRenderingMode` to return client mode (named
in S2c.3 "Tests that break").

### D2 — S3.1: when the client sends `set_dark_theme`

**Decision.** At first connect only: `useServerVtk` sends `set_dark_theme({dark})` once per probe session, only when
`visorArgs.darkMode != null`, awaited, before it fetches `get_visor_scene_details_json` (from S3.3b; in S3.1 there
is no fetch yet). Sender: `trame.trigger('set_dark_theme', [{ dark }])`.

Not on a prop change, because no prop-change path exists [src]:
- `Visordash.react.js` writes `window.__visorArgs.darkMode = darkMode` inside the effect that begins
  `const visorArgs = (window.__visorArgs ??= {});` and closes `}, []);` (line 78): it runs at mount only.
- `App.tsx` reads `window.__visorArgs` once into a ref (`if (visorArgs.current == null) { … }`), moved to
  `useVisorArgs` in S2c.0 with the same read-once behaviour.
So a later Dash `darkMode` change reaches neither the client theme in CLIENT mode today nor the server in SERVER
mode. Sending "on prop change" would be dead code.

Why before the fetch: the server's `set_dark_mode` writes `_ui_state.dark_theme` (`vtk/scene/server_scene.py:72`,
`def set_dark_mode`) [src], so the scene details fetched next already carry the prop's theme, and
`buildFrontendAsync`'s darkMode override applies the same value. Ordering is guaranteed because the send is awaited
before the fetch is issued.

When `darkMode` is null/undefined (standalone page): nothing is sent; server background and client theme both come
from the server's own `dark_mode`.

A failed send is logged (`[VISOR] set_dark_theme send failed`) and the build continues: the only cost is a
background that does not match the page theme.

Rejected:
- "Both": the prop-change half has no source (above).
- On every rebuild: in 4.2/4.3 there is exactly one build per session, so it equals "first connect"; whether an S4
  rebuild re-sends is S4's (carried, §9 item C1: `load_state` can restore a different theme on the server).

**Silent failure:** not sending (or sending after the fetch) leaves the server background on the server default
while the client theme follows the prop; nothing fails. Pinned by S2c.3+S3.1 pin 4; manual check reads the frame
background.

### D3 — S3.3: whether `setGeometryHighlightAsync` stays on `IRenderer`

**Decision: it stays.** Settled from its caller, as C-7 settled `addCameraSettledListener`.

Callers (search `setGeometryHighlightAsync` in client `src`, all files) [src]:
- `VisorFrontend.tsx:184` — `renderer.setGeometryHighlightAsync(result).catch(() => {});` inside
  `this.pickGeometryAsync`, which is called only from `VisorFrontend.tsx:192` (the constructor's
  `renderer.addViewerClickedListener` geometry listener).
- Implementations: `IRenderer.ts:251`, `NullRenderer.ts:264`, `WasmRenderer.ts:597`. No jest test calls it
  (search in `jest-tests` → no match).

C-7's caller, `attachCameraSyncReporter` (`CameraSyncReporter.ts:111`), is attached only by the client-mode hook
after S2c.1, so moving the method to `WasmRenderer` costs no mode check. `setGeometryHighlightAsync`'s only caller
is in `VisorFrontend`, which ruling 9 keeps mode-independent. Removing the method from `IRenderer` would make
`VisorFrontend` narrow its renderer to `WasmRenderer` (an `instanceof`, i.e. a mode check outside the hooks) or
take a second, wasm-only collaborator. Both contradict ruling 9.

`ServerRenderer.setGeometryHighlightAsync` rejects with `GeometryPickingUnavailableError`. It is unreachable,
because `ServerRenderer.pickGeometryAsync` always throws first. **Ruling 12 inert stand-in:** named; its home is the
later story "Geometry picking in remote mode" (ruling 3), which needs a server-drawn highlight anyway.
Rejecting (not resolving) makes a future caller that skips the pick fail loudly.

Rejected:
- Fold the highlight into `pickGeometryAsync` (WasmRenderer draws inside the pick), removing the member: changes
  the local pick contract and the `.catch` structure of local code for a one-line stand-in.
- No-op body: a silent stand-in; if ever reached it would hide the missing feature.

`clearGeometryHighlight` stays and is a **true no-op** on `ServerRenderer` (no highlight exists); it cannot throw,
because `setSelectionMode` calls it on every mode change (`VisorFrontend.tsx:166`) [src].

### D4 — the client-rendering hook's name

**Decision: `useClientVtk`.** (The prompt's "useCLientVtk" is read as a typo for this.)

- Ruling 9 allows "(or equivalent naming)" and "room to propose other names".
- Ruling 19's "Existing Local names stay" covers existing names; the hook is new. No client file contains
  `useLocalVtk` (search `useLocalVtk` in `src`, `tests` → no match; only `phase4_plan_v2.md`) [src].
- It matches the enum (`RenderingMode.CLIENT`), the wire value `"client"`, the probe's branch, and pairs with

Rejected: `useLocalVtk`, which matches 8.1's mapping and the server's existing `LocalApp`/`VisorVTKLocal`, but 8.1's
mapping predates ruling 19 and would leave the one new client name carrying "Local" beside `useServerVtk`.

### 6.7 `rca/ServerCanvas.ts` (new, S3.1; extended S3.2)

```ts
/** The RCA area name; must equal RCA_AREA_NAME in app/trame/server_app.py. */
export const RCA_AREA_NAME = 'view';
/** The part of a wslink session the canvas uses. */
export type RcaSession = {
    subscribe(topic: string, callback: (args: unknown[]) => void): { unsubscribe(): unknown };
    call(method: string, args: unknown[]): Promise<unknown>;
};
/** Pixel size of the last frame drawn. */
export type FrameSize = Readonly<{ width: number; height: number }>;
/** A click on the canvas in VTK-normalised coordinates (origin bottom-left). */
export type CanvasClick = Readonly<{ normX: number; normY: number; ctrlKey: boolean; shiftKey: boolean }>;
/** What ServerRenderer needs from the canvas. */
export interface IServerCanvas {
    readonly element: HTMLDivElement;
    readonly frameSize: FrameSize | null;
    addFrameListener(callback: (fps: number) => void): () => void;
    addClickListener(callback: (click: CanvasClick) => void): () => void;
}
export class ServerCanvas implements IServerCanvas {
    /** Subscribe to the area's frame stream on session and draw each frame into element. */
    constructor(session: RcaSession, areaName: string);
    /** The element that shows the frames; UiScaffold hosts it as it hosts the wasm canvas. */
    readonly element: HTMLDivElement;
    /** Natural size of the last decoded frame, or null before the first. */
    get frameSize(): FrameSize | null;
    /** Call callback once per drawn frame with frames per second over the last second; returns its remover. */
    addFrameListener(callback: (fps: number) => void): () => void;
    /** Call callback once per click (press and release at one point); returns its remover. */
    addClickListener(callback: (click: CanvasClick) => void): () => void;
    /** Unsubscribe, remove DOM listeners and revoke the current frame URL. */
    dispose(): void;
}
```

### Increment summaries

- **S2c.0 — Move client wiring into `useClientVtk`.** Pulls today's wasm bootstrap, state-publish and resize logic
  out of `App.tsx` into a new hook, unchanged in behavior. Risk: the single effect in `App` today secretly does two
  things (bootstrap once, then publish on every frontend change), so splitting it needs an equivalence argument,
  not a blind copy-paste.
- **S2c.1 — Reporter attach/release ordering.** Moves the `CameraSyncReporter` attach/detach into the hook and adds
  `VisorFrontend.release()`, which also stops stale geometry-click listeners from firing (change C-4). Risk: the
  attach-new/release-old ordering around an `await` must guarantee exactly one reporter is ever attached, and this
  increment is also the first to introduce `jest.mock(` in the suite, which is a carried unknown.
- **S2c.2 — Shared `buildFrontendAsync`.** Extracts the frontend-building logic (parse → version-check → build
  renderer/frontend) into its own function so both client and server hooks can reuse it later. Low risk: it's a
  small, test-guarded extraction with no behavior change.
- **S2c.3 + S3.1 — Probe, mode branch, frame streaming, theme.** The biggest and riskiest increment: adds the
  `rendering_mode` probe, makes `App.tsx` branch into client/server paths without ever loading wasm on the server
  path, wires up `ServerCanvas` to receive and decode RCA video frames, and sends `set_dark_theme` on connect.
  Deliberately combined into one commit per explicit instruction, because splitting it would let the server branch
  render with an empty canvas. Includes a transitional direct-DOM mount that S3.3b later removes.
- **S3.2 — Mouse/wheel/click forwarding.** Forwards mouse button, move, wheel and click events from `ServerCanvas`
  to the server over `trame.rca.event`, with the y-axis flipped to match VTK's bottom-left origin. Risk/note: there
  is no jest test harness for the real `VtkScene.js` (it requires wasm), so the manual check is the only safety net
  for that one file; can be developed in parallel with S3.3a since their file sets don't overlap.
- **S3.3a — Extract `SceneTriggerSends`; move `addCameraSettledListener`.** A pure refactor: pulls the trigger-send
  helper out of `WasmRenderer` and relocates `addCameraSettledListener` off the shared `IRenderer` interface onto
  `WasmRenderer` only, since the server renderer has no equivalent. Lowest-risk increment — mechanical, with an
  existing strong test net and only a type-level pin (`tsc --noEmit`).
- **S3.3b — `ServerRenderer` and the server frontend.** Builds the actual server-mode renderer: a local camera
  cache fed by `server_camera_state` updates, per-part toggle sends, and `UiScaffold` hosting for the server canvas
  (replacing S2c.3+S3.1's transitional direct mount). Risk: the cache must never re-send `sync_camera` on its own
  echo (rulings 24, 25) — getting this wrong causes a silent camera feedback loop that only a dedicated pin and a
  manual "does the readout follow a reset" check would catch.
- **S3.4 — Picking (P1, part-select only).** Wires up `ServerRenderer`'s click listener to send `pick_part_at` in
  render-window device pixels (not CSS pixels × dpr) and fan the result out to every registered viewer-clicked
  listener exactly once per click. Risk: the CSS-vs-device-pixel distinction is an easy, silent way to pick the
  wrong part; geometry (vertex/edge) picking is explicitly out of scope and instead rejects with a named error.
