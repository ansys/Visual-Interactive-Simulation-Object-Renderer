### 1.1 trame-rca 2.11.8 as installed [src, venv `trame_rca/`]

trame-rca 2.11.8 is restructured against the 2.4.0 that Section 7.0 read. Files: `protocol.py`, `utils.py`,
`view_adapter.py`, `vtk_utils.py`, `rca/{protocol,vtk_rca,__init__}.py`, `schedulers/{image_scheduler,protocol,
video_scheduler,__init__}.py`, `encoders/*`, `widgets/rca.py`, `module/__init__.py` [run, directory listing].

- **Window protocol.** `trame_rca.rca.protocol.RemoteControlledAreaProtocol`, `@runtime_checkable`.
  `img_cols_rows` is a **`@property`** returning `tuple[NDArray, int, int]`; `process_resize_event(width, height)`;
  `process_interaction_event(event: dict)`. There is no `AbstractWindow`.
- **`window_wrapper(window)`** (`rca/__init__.py`) returns the object unchanged if it passes `isinstance` against the
  protocol, wraps a `vtkRenderWindow` in `VtkRemoteControlledArea`, else raises `RuntimeError`.
- **`VtkRemoteControlledArea(vtk_render_window)`** (`rca/vtk_rca.py`; `utils.VtkWindow` and `vtk_utils.VtkWindow`
  are aliases of it). Constructor: `GetInteractor()`, `iren.EnableRenderOff()`, `ShowWindowOff()`, a
  `vtkWindowToImageFilter` (RGBA, back buffer, `ShouldRerenderOff`). `img_cols_rows`: `Render()`, then capture, then
  returns `np.ascontiguousarray(np_image[::-1])[..., :3]` — **a fresh copy** (an RGB view over a new RGBA buffer).
  `process_resize_event`: `iren.UpdateSize(w, h)`, plus `WindowResizeEvent` only for VTK < 9.5.
  `process_interaction_event`: returns on `StartInteractionEvent`/`EndInteractionEvent`, else
  `vtkRemoteInteractionAdapter.ProcessEvent(iren, json.dumps(event))`; the bool result is discarded.
- **Scheduler** `schedulers/image_scheduler.RcaImageRenderScheduler`. The constructor calls
  `asynchronous.create_task(self._render())` and `create_task(self._push())`. `schedule_render()` =
  `self._request_event.set()` on an `asyncio.Event`. `_render` loop: `await event.wait()`, `event.clear()`,
  `_render_frame(interactive)`; if interactive ≠ still quality, `_wait_for_still` **clears the event first**, then
  sleeps up to five target periods, returning early if the event is set again; otherwise renders at still quality.
  `_render_frame` reads `self._rca.img_cols_rows` **synchronously on the loop thread** and hands the array to
  `loop.run_in_executor(ENCODING_POOL, encode, ...)`. `_push` awaits each encode and calls the push callback if its
  `m_time` is not older than the last push.
- **Adapter** `view_adapter.RcaViewAdapter(window, name, *, scheduler=None, ...)`. With `scheduler=None` it builds
  `RcaImageRenderScheduler(window, push_callback=self.push)` (defaults: jpeg, 30 fps, interactive 50, still 90).
  `update_size`: clamps w/h to ≥ 10, stores `(w, h, p)`, calls `self._rca.process_resize_event(*self.image_size)`
  then `schedule_render()`. `image_size` is `(300, 300)` until the first size. `on_interaction`: drops a release with
  no matching press (reads `event["type"]`), scales `x`, `y`, `w`, `h` by `scale_factor`, calls
  `self._rca.process_interaction_event(event)`, then `schedule_render()`.
- **Widget** `widgets/rca.RemoteControlledArea(name=None, display="image", **kwargs)` is an `HtmlElement`; its
  constructor calls `self.server.enable_module(module)`. `add_view_handler` registers at once if
  `self.server.running`, else queues for `_on_ready`. `create_view_handler(window, encoder=None, target_fps=30.0,
  interactive_quality=60, still_quality=90, ...)` builds a scheduler **only** when `display == "video-decoder"` or
  `encoder` is truthy; with `encoder=None` the quality and fps arguments are not used (the adapter builds the default
  scheduler).
- **Protocol** `protocol.StreamManager(LinkProtocol)`: RPCs `trame.rca.drop`, `trame.rca.size`, `trame.rca.push`,
  `trame.rca.event`, `trame.rca.reset`, `trame.rca.video.codecs`, `trame.rca.video.negotiate`. `update_size` and
  `on_interaction` `print` and drop the call for an unknown area. **`push_content` reads
  `self.coreServer.network_monitor.pending`** before `publish("trame.rca.topic.stream", ...)`.
- **Module setup** (`module/__init__.py`): `configure_protocol(root_protocol)` creates the `StreamManager`, sets
  `server.controller.rc_area_register` / `rc_area_unregister`, and calls `root_protocol.registerLinkProtocol(...)`.

### 1.2 The eight S1.0 items

**Item 1 — Threads.**
- Trigger handlers run on the trame event-loop thread: `CoreServer.trigger` is `async def` behind
  `@exportRpc("trame.trigger")` and runs `fn(*args, **kwargs)` inside `with self.server.state`
  (`trame_server/protocol.py`) [src]. The loop is the `AsyncRunner` thread:
  `TrameServerManager._start_core` calls `self._server.start(thread=self._async_runner.thread, exec_mode="coroutine")`
  [src, `app/trame/trame_server_manager.py`].
- `VisorVTK` public operations (`start`, `update`, `add_dataset`, `remove_dataset`, `clear`, `update_variables`,
  `load_state`) are synchronous and contain no marshalling, so they run on the caller's thread
  [src, `app/visor_vtk.py`]. `save_state` and `_start_async` are coroutines on the caller's loop [src].
- `on_server_ready` is called from `CoreServer.port_callback` [src]; that it runs on the loop thread is [inf].
  The design below makes that assumption fail loudly (`asyncio.get_running_loop()` in `bind`, Section 5.5).
- Consequence [inf from the two src rows]: every `_vtk_lock` holder is either a caller thread or the loop thread, and
  a trigger arriving while a caller thread holds the lock blocks the whole loop (each coordinator method does
  `with self._vtk_lock`, `vtk/scene/base.py`) [src]. This is true in local mode today and is not changed by Q-1.

**Item 2 — State writes from a non-loop thread.** Not safe; marshal.
- `State.flush` → `push_state_change` → `self.publish(...)` (`trame_server/protocol.py`) [src]. wslink
  `PublishManager.publish` → `schedule_coroutine(0, protocol.sendWrappedMessage, ...)` (`wslink/publish.py`) [src].
  `schedule_coroutine` takes `asyncio.get_event_loop()` **on the calling thread**, or creates and sets a new loop if
  there is none, then `loop.call_later(...)` (`wslink/__init__.schedule_coroutine`) [src].
- Search `call_soon_threadsafe` and `run_coroutine_threadsafe` over venv `trame_server` and `wslink`: no match [run].
- Consequence [inf]: from a caller thread with no running loop, the send is scheduled on a loop that never runs (lost,
  silent); from a thread with its own running loop (a Jupyter kernel), the send runs on the wrong loop. Every state
  write in S1.6a, S1.7 and S4.1 is therefore marshalled onto the trame loop. Ruling 4's "unless shown safe" is
  answered: not safe.
- Local mode's `LocalView.update` → `js_call` from the caller thread takes the same publish path. How it is
  delivered in practice: **cannot determine**; out of S1's scope (Section 9).

**Item 3 — Where `Render()` runs.**
- trame-rca 2.11.8: `Render()` runs in `VtkRemoteControlledArea.img_cols_rows`, called synchronously from
  `RcaImageRenderScheduler._render_frame` on the loop thread (1.1) [src].
- Server `Render()` calls — search `.Render()` in server src: `local_renderer.py` `VisorLocalRenderer.render` and
  `VisorLocalRenderer.render_window_only` [run]. No other.
- Paths to them — search `_push_runtime_state(`: definition `vtk/scene/base.py` (`VisorSceneBase`), one call in
  `VisorSceneBase.apply_state` (inside `with self._vtk_lock`), override in `local_scene.py` [run]. Search
  `render_window_only(`: definition, two docstring lines in `base.py`, one call in `VisorLocalScene._push_runtime_state`
  [run]. Search `self.render(`: `VisorSceneBase.finalize_scene` and `VisorSceneBase.update_variables_for_dataset`,
  both inside `with self._vtk_lock` [run]. Search `_scene.render(`: `VisorVTK.remove_dataset` [run], which reaches
  `VisorSceneBase.render`, itself `with self._vtk_lock` [src].
- Ruling: in local mode every `Render()` VISOR issues holds `_vtk_lock` [src, rows above]. The carried caller list is
  closed.

**Item 4 — Calling trame-rca's scheduling from a non-loop thread.** Neither is safe.
- `schedule_render` sets an `asyncio.Event` (1.1) [src]; `asyncio.Event` is not thread-safe [inf, stdlib contract],
  so a set from a caller thread may not wake the loop.
- The scheduler constructor calls `trame.app.asynchronous.create_task`, which takes `asyncio.get_event_loop()` and
  falls back to a new, set loop on `RuntimeError` [src, `inspect.getsource`]. Built off the loop thread, its two tasks
  land on a loop that never runs [inf]: **silent**, no frame ever.
- Consequence: the view handler (adapter + scheduler) is built on the loop thread, in `on_server_ready` (C-8 holds,
  now for a second reason), and every frame request is marshalled with `loop.call_soon_threadsafe`.

**Item 5 — Interaction event format.**
- `vtkRemoteInteractionAdapter` docstring: "Map vtk-js interaction events to native VTK events … For the expected
  format see … vtk-js … InteractorStyleRemoteMouse"; `ProcessEvent(iren, event: str, devicePixelRatio=1.0, …) -> bool`,
  "true if the event is processed, false otherwise" [run, `__doc__`].
- `RcaViewAdapter` reads `event["type"]` and scales `x`, `y` (1.1) [src]. The bundled trame-rca client
  (`module/serve/trame-rca.umd.js`) contains `ButtonPress`, `MouseWheel`, `StartInteractionEvent` [run, literal
  search]. The spike canvas's `{t, p}` shape is the base `AreaAdapter.on_interaction` shape, which `RcaViewAdapter`
  does not use [src].
- Consequence: `RemoteCanvas` (S3.2) must send the vtk-js remote-mouse shape keyed on `type`. An unrecognised event
  returns `False` and trame-rca discards it: **silent** (Section 9; S3.2/S5).

**Item 6 — Encode buffer lifetime and reuse.** Safe on both counts.
- *Lifetime.* trame-rca's capture returns a fresh contiguous copy from `img_cols_rows` (1.1) [src], so the next
  `Render()` cannot overwrite an array that the pool is still encoding.
- *Reuse* (ruling 7). With the lock held, `VisorRcaWindow` returns the same array object again (Section 4). With
  interactive ≠ still quality, the scheduler also encodes twice per request. So one array can be in two encodes at
  once. Each step from the unpack to the encode is listed below. **None writes the frame array.** Read in this pass:
  trame-rca 2.11.8, Pillow 13.0.0 [run, `PIL.__version__`].
  1. `RcaImageRenderScheduler._render_frame` (`schedulers/image_scheduler.py`): `np_img, cols, rows =
     self._rca.img_cols_rows` is a tuple unpack. `loop.run_in_executor(self._encode_pool, self._rca_encoder.encode,
     np_img, cols, rows, quality)` passes the reference [src].
  2. `RcaImageEncoder.encode` (`encoders/image_encoder.py`): reads the clock, opens `profiler.timer(...)`, then calls
     `self._impl(np_image, self.value, cols, rows, quality, now_ms)`. `_impl` returns `encode_pil` for every member
     except `TURBO_JPEG`, so `"jpeg"` (5.7) takes the Pillow path [src].
  3. `pil.encode` (`encoders/pil.py`) builds `meta` from `cols`, `rows` and `quality`, then calls
     `encode_np_img_to_bytes` [src].
  4. `rgbx_view(image)` (`encoders/img.py`) reads `base`, `dtype`, `ndim`, `shape`, `flags.c_contiguous`, `strides`
     and `ctypes.data` [src].
  5. One of two branches runs:
     - **Capture frame** (an RGB view over a contiguous RGBA copy, so `rgbx_view` returns the base). It calls
       `Image.frombuffer("RGBX", (w, h), rgbx, "raw", "RGBX", 0, 1)`. `"RGBX"` is in `_MAPMODES`, so Pillow
       maps the buffer with `core.map_buffer(...)` and sets `im.readonly = 1` (`PIL/Image.py` `frombuffer`) [src].
       The `convert("RGB")` branch is skipped for JPEG.
     - **Placeholder** (`np.full`, `base is None`, so `rgbx_view` returns `None`). It calls `Image.fromarray(image)`
       → `frombuffer("RGB", ...)`. `"RGB"` is not in `_MAPMODES`, so it falls through to `frombytes`, which
       copies [src].
  6. `image.save(fake_file, "jpeg", quality=...)` (`PIL/Image.py` `save`). The image is not an `ImageFile`, so
     `save` takes the `self.load()` branch and skips `_ensure_mutable`. `load` skips the palette branch (no palette)
     and returns `self.im.pixel_access(self.readonly)` [src]. Then `JpegImagePlugin._save` builds `encoderconfig`
     from `encoderinfo` and calls `ImageFile._save(im, fp, [_Tile("jpeg", ...)], bufsize)`. That runs `im.load()`,
     then `_encode_tile`: `encoder.setimage(im.im, extents)` and `encoder.encode(...)` [src]. The C JPEG encoder
     reads the image memory and writes only to its output buffer [inf, C source not read].
  7. `_push` receives `(bytes, meta, m_time)`; the array is no longer referenced [src].
- The turbo path (`encoders/turbo_jpeg.py`) is not taken with `"jpeg"`. For the record, it passes the array to
  `TurboJPEG.encode` [src].
- Consequence: returning the same frame object while the lock is held is safe. `VisorRcaWindow` never writes a
  returned array in place (Section 4).

## 4. Q-1: what `VisorRcaWindow.img_cols_rows` returns when `_vtk_lock` is held

Ruling 16 settles Q-1 as try-and-reschedule. This section is the contract S1.4 writes.

**Why the reschedule cannot be skipped.** Every locked operation ends by requesting a frame from inside its own
locked region: `finalize_scene` → `render()`, `update_variables_for_dataset` → `render()`, each per-part apply →
`_publish_*` (Section 5). The loop may take that request while the caller still holds the lock. If the window then
returned without asking again, no later request would come and the client would keep the pre-operation frame.
**Silent** [inf from item 3's call chains].

**Contract of `img_cols_rows`** (runs on the loop thread; the lock is `VisorSceneBase._vtk_lock`, an `RLock`):

1. `vtk_lock.acquire(blocking=False)`.
2. **Acquired.** In a `try`/`finally` that releases:
   a. if a size was recorded since the last locked frame, call `renderer.set_viewport_size(w, h)` once, with the
      **last** size recorded, and clear it. Earlier sizes are not applied (ruling 1: resize coalesces);
   b. forward every queued interaction event to `capture.process_interaction_event`, in arrival order, and empty the
      queue. This includes events queued across any number of earlier held-lock calls. None is dropped or merged
      (ruling 1);
   c. `frame = capture.img_cols_rows` (this is the `Render()` and the read-back);
   d. keep `frame` as the last frame; return it unchanged.
3. **Not acquired** (another thread holds the lock):
   a. no `Render()`, no read-back, no resize, no event forwarded. The recorded size and the whole queue are kept;
   b. call `reschedule()` exactly once;
   c. return the **last frame object itself** (`is`-identical to what step 2d last returned); or, if no frame was
      ever captured, a **placeholder**: `(array, cols, rows)` with `array` of shape `(rows, cols, 3)`, dtype `uint8`,
      every pixel `round(c * 255)` of `renderer.background_rgb`, at the last size `process_resize_event` received,
      or `(300, 300)` before any. 300×300 is the size trame-rca reports before any resize (1.1).

`reschedule` is `RemoteLoopBridge.retry_frame`. If no retry is pending, it marks one pending and calls
`loop.call_later(RETRY_DELAY_S, self._fire_retry)`, with `RETRY_DELAY_S = 0.1`. `_fire_retry` clears the mark, then
calls `view_handler.schedule_render()`. **While a retry is pending, `retry_frame` does nothing** (ruling 6). Two
locked calls before the delay expires leave one pending retry, not two. The call is delayed rather than a direct
`schedule_render()` because `_wait_for_still` clears the request event right after `_render_frame` returns (1.1)
[src]. A set made inside `img_cols_rows` would be erased and the retry lost; written as a direct call, this is
**silent** [inf from src]. While the lock stays held, this retries about every 0.1 s and pushes one stale or
placeholder frame per retry.

Rejected alternatives:
- **Raise, or return `None`.** The tuple unpack in `_render_frame` fails inside the render task. The task dies, and
  the stream stops for the life of the server.
- **Blocking acquire.** Rejected by ruling 16. It stalls all websocket I/O for the length of any locked operation.
- **A custom scheduler that skips the frame.** This would duplicate `RcaImageRenderScheduler`'s render, encode and
  push loop (ruling 12). Overriding its `_render_frame` would depend on a private member.

**How the lock tests observe it** (`tests/unit/renderer/test_remote_window.py`, S1.4). The lock is a real
`threading.RLock`. It is held by a **second thread**: thread B acquires it, sets a `held` event, and waits on a
`release` event. Every join has a timeout. A same-thread hold would be vacuous: the `RLock` is re-entrant, so
`acquire(blocking=False)` would succeed and the test would pass with the lock check deleted. The capture is a
recording double. Its `img_cols_rows` property counts accesses and returns a hand-written literal frame. The
reschedule is a recording callable. The renderer is a real `RemoteRenderer` built with a recording sink and
`background_rgb=(0.2, 0.4, 0.6)`.

## 6. Decisions (each with the alternative it rejects)

- **D-1 — Compose trame-rca's `VtkRemoteControlledArea` as the capture**, not re-implement it. It is public (in
  `rca.__all__`), its returned array is a copy (item 6), and it disables interactor renders. Rejects: copying the
  capture into `VisorRcaWindow` (a duplicate, ruling 12) and subclassing it (C-2's private-member objection). C-2 is
  given as adopted (ruling 14); my findings support it, with composition as its form.
- **D-2 — Resize and interaction are applied in `img_cols_rows`, under the lock.** Rejects: applying them unlocked
  on the loop thread, which races caller-thread VTK writes. `_vtk_lock` "Serialises every server-side VTK mutation"

### 11.2 PR descriptions

**S1.1 — Pin trame-rca and wslink.**
Pins `trame-rca` to `2.11.8` and adds `wslink >= 2.6.0`. The first `trame-rca` commit used `"*"` and relocked 26
unrelated packages. This redo keeps the lock change to what these two pins require. trame-rca's API changed
substantially between 2.4.0 and 2.11.8 (the window protocol was renamed and `img_cols_rows` became a property), so an
unpinned upgrade could break the remote stack without warning. wslink 2.6.0 is the version where `coreServer` is set on
registered protocols, which trame-rca's push path needs.

**S1.2 — Extract `VtkPipelineRenderer`.**
Moves the VTK pipeline that local and remote rendering share out of `VisorLocalRenderer` into a new abstract base:
renderer, window, interactor, widgets, per-part pipelines, and camera and cross-section writes. Local-only delivery
(wasm serialisation) remains in `VisorLocalRenderer` behind four `_publish_*` hooks. `pick_geometry` moves off
`IRenderer` and `VisorSceneBase` onto the local classes, because remote picking works differently. Local behaviour
does not change, and no tests are added or removed. The only test change re-points seven patch targets.

**S1.3 — Add `RemoteRenderer`.**
Adds an off-screen renderer built on the shared base. Each write ends by asking its sink for a frame; it never calls
`Render()` itself, so every render happens on the streaming path under the scene lock. Adds `set_viewport_size`,
`pick_part_at` (cell picker, no render pass), real cross-section and bounding-box visibility, and a `None` renderer
annotation. Documents the per-part contract in both the Python and the TypeScript `IRenderer`. A parity suite checks
that local and remote apply each part field the same way.

**S1.4 — Add `VisorRcaWindow` and `RemoteLoopBridge`.**
Adds the trame-rca area that captures frames from the remote renderer. It touches VTK only while holding the scene
lock. If another thread holds the lock, it returns the last frame (or a placeholder in the background colour) and
schedules one delayed retry. Resize and mouse events are queued and applied under the lock at the next frame: events
in order with none dropped, and only the last resize. The bridge carries frame requests and state writes from any
thread onto the trame event loop. It deduplicates pending retries and uses a delayed call, because a direct one
would be erased by trame-rca's own scheduler. Removes the need for the spike's monkey-patches.

**S1.5 — Extract `SceneTriggerApp`.**
Moves the scene triggers shared by every rendering mode, plus the HTTP and lifecycle setup, from `LocalApp` into a
base class. `LocalApp` keeps its constructor and its three local-only triggers. Each app publishes `rendering_mode`
in state before start. A test pins the exact local trigger list, which catches both a missing and a doubled
registration.

**S1.6a — Add `VisorRemoteScene`.**
Adds the scene coordinator for remote mode. It builds the remote renderer and the RCA window over the scene's lock,
picks parts under the lock, and requests a frame after `load_state`. The streamed JPEG has no transparency, so the
window background follows the client's theme CSS. It is re-coloured when a loaded state changes the theme, and when
the client reports its theme through `set_dark_mode`.

**S1.6b — Add the REMOTE rendering mode.**
Adds `RenderingMode.REMOTE`, `VisorVTKRemote` and `RemoteApp`. `RemoteApp` serves the shared triggers plus
`pick_part_at` and `set_dark_theme`, creates the trame-rca area before the server starts, and binds the stream once
the server is ready. An integration test starts a remote viewer and checks that a first frame reaches the stream with
no client attached. Local mode and its triggers are unchanged.

**S1.7 — Publish `remote_camera_state`.**
After `reset_camera`, `sync_camera` and `set_projection`, the remote renderer publishes the camera record as the state
key `remote_camera_state` (seven camelCase fields, or `None`), written on the event-loop thread. Remote clients need
this for camera-dependent UI, such as the ruler, because they have no local VTK camera to read.

### 11.3 Sessions

- **Every increment gets its own dedicated session.** None share one (Section 7). Each has a distinct risk subject:
  a large move (S1.2, S1.5), a new renderer (S1.3), concurrency (S1.4), theme and pick (S1.6a), end-to-end wiring
  (S1.6b), and camera state (S1.7). Putting two in one session would mix their contexts and weaken each
  increment's review.
- **S1.1 needs no agent session.** It is done by hand and must land first.
- **What can run in parallel:** S1.5 depends on none of S1.2–S1.4, so its session can run alongside that chain in a
  separate session and worktree. It must merge before S1.6b starts.
- **Strictly sequential:** S1.2 → S1.3 → S1.4 → S1.6a → S1.6b. S1.7 starts after S1.4 and S1.6a. It can run
  alongside S1.6b in a separate session, because their file lists do not overlap (Section 7). S1.7 touches
  `remote_renderer.py`, `remote_loop_bridge.py` and their tests; S1.6b touches neither.
- **Model choice:** use the strongest reasoning model for S1.4. Use a strong coding model for S1.2, S1.3, S1.5,
  S1.6a and S1.6b, and a standard one for S1.7.
